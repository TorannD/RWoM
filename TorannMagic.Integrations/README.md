# RWoM Integrations

This directory is an independent RimWorld 1.7 mod, not another load folder of the parent RWoM mod.

## Current contents

- MedPod: excludes Arcane Weakness from treatment, when the original MedPod name gate matches.
- Hellsing ARMS Ultimate: retains the original holy/decay damage integrations and original name gate.
- Kure: connects the stamina-potion addiction to its chemical need when the relevant definitions exist and no link is already present. A fixed Kure version remains authoritative.

- VGE 1/2: conditional XML, fuel providers/refunds, gravengine power, oxygen pipe output, beam interception and boarding-pod landing adapters. The assembly identity remains `TorannMagic.VGE`.

- Ability AI: with `saintwacko.AbilityAI` present, the conditional `TorannMagic.AbilityAI` assembly hands RWoM autocast ownership to Ability AI. A Core CastOwnership provider makes every RWoM automatic casting path (colonist autocast, NPC AI casting, the aggressive decision tree, travel autocast) stand down for pawns whose bridged spells Ability AI handles; a claim hook keeps NPC casts working with "Also use abilities no mod claims" off; the bridge gizmo gains Ability AI's right-click autocast menu and mode badge, and the classic autocast toggle writes are suppressed for spells Ability AI rules. Without Ability AI the assembly does not load and classic RWoM autocast is untouched. Rule XML lives in the conditional `v1.7/AbilityAICompat/Patches` root, generated by `scripts/generate-abilityai-rules.py` from the bridge defs: 250 spells ruled across two batches — single-target and area damage (radii from the projectile defs), movement/teleport, creature summons (Deploy), pain/bleeding heals, firefighting, smoke cover, and NPC gates for instant-kill and base-wrecking casts. Deliberately unruled: management/utility spell families (dismissals, identity changes, social and world-utility, upkeep auras without hediff gates) stay player-decided, and golems plus the animal/demon direct-projectile controllers stay with RWoM.

- HAR: existing RWoM race/backstory trait restrictions, with actual race-type detection.
- Pawnmorpher: retain progression components during race reconciliation.
- Giddy-Up / Simple Sidearms: mounting and remembered-weapon bridges, including the installed 1.7 forks.
- Legacy policies: existing Prison Labor, No Job Authors and Children hooks; legacy name gates retained.
- Multiplayer: conditional synchronization adapter, with the original public Content facades retained.
- Isekai Dungeons: conditional RWoM dungeon definitions; no duplicate leveling bonuses.
- Logging Framework: optional provider backend with safe Content-owned fallback.

These adapters have focused verification. Multiplayer has also passed a live two-process, two-map Blink check with matching payment, cooldown and destination on both peers. This is not a claim that every ability or combination of third-party mods is multiplayer-safe. Official DLC support, general ability safety and class-progression data remain in RWoM. Detailed release evidence and known exclusions are recorded in the repository's integration plan and external verification artifacts.

## Installation status and version pairing

**Install matching releases of all three packages together.** Do not combine this directory with an older RWoM version that still owns the extracted adapters: patches can apply twice. Package version 0.1 alone is not a compatibility guarantee.

For a matched source installation, the main package must no longer contain `v1.7/Patches/MedPodx.xml`, `Hellsing_DamageTypex.xml`, `KureStaminaPotion.xml` or the old `v1.7/VGECompat` and `v1.7/IsekaiCompat` roots. The matching main DLL must omit the extracted external adapters and startup registrations. Do not leave old TorannMagic.VGE or TorannMagic.Multiplayer binaries under a Content load root. The migration installer verifies the reviewed removal manifest and backs up changed files before delivery. Do not copy the nested directory into the game's mod list while retaining an old main package.

Requires matching RWoM Core (including the CastOwnership API) and A RimWorld of Magic (Continued). Load this package after Core, RWoM, Kure and VGE 1/2 (if present). Other integration targets are optional; no target code or assets are bundled. The VGE assembly is built from `Source/TorannMagic.VGE` and delivered only under the conditional `v1.7/VGECompat/Assemblies` root. It must never be copied into the unconditional Assemblies folder. Core stays free of third-party references.

## Saves and rollback

VGE component names and the `TorannMagic.VGE` assembly identity are retained. Oxygen mode, pending paid oxygen and pulse time remain saved on the original RWoM pump. The new output comp has no saved state. Boarding-pod Scribe keys and VGE passenger-container ownership are unchanged. Keep Integrations enabled on saves that use its VGE components; disabling it is not a supported uninstall procedure.

Keep matched main/integration versions. Roll back both from the installation backup. Never roll back only one package and leave two patch owners active.

## Development

The active plan is `../docs/integrations/plan.md`. Test through the parent repository's `tests/run-regression-tests.ps1` with an external artifacts directory and filter `IntegrationPackage,StaminaPotionAddictionNeed`. Test target absence and presence and preserve existing patch semantics. New compatibility features are separate tasks from extraction.

Do not move persisted C# types without native save/load proof. Keep third-party types out of Core contracts. Do not automatically modify the player's ModsConfig.

### Content extension boundaries

`IMagicalOxygenOutput` lives beside the Content-owned oxygen pump: one attached output comp owns a pulse and obtains paid supply through `SupplyPulse`. It must retain undelivered paid credit. `IMagicalShieldProjectileAdapter` creates a landing plan before shield payment; `Commit` runs only after successful payment. Register once per adapter type, without capturing maps in the registry. These are gameplay-specific contracts and intentionally do not introduce a Core dependency on Content. Native Odyssey beam handling stays in Content.

### Kure and VEF/VPE

The unconditional `TorannMagic.Integrations.dll` contains name-based optional probes and Harmony fixes, with no reference to Kure, VEF or VPE assemblies. Kure trait degree repair preserves saved owners and supports roster previews. VEF/VPE active-job/warmup detection registers with Core's CastOwnership API. General custom-class definitions, classic progression and grimoire display stay in Content. Removing Integrations removes these compatibility safeguards, not the underlying general custom-class system.

### Pawnmorpher

The optional race-comp pruning patch belongs to Integrations. It preserves the original magic, might, knowledge and progression component instances through Pawnmorpher's reconciliation, including an exceptional exit. It does not replace Pawnmorpher's race change, port the entire mod to 1.7 or reconstruct already discarded data. The implementation references the existing JecsLite AbilityUser base classes, not a Pawnmorpher assembly; detection of the target method remains optional. Keep Integrations enabled when using this compatibility safeguard.

### Isekai Dungeons

The existing RWoM dungeon definitions now belong to the conditional `v1.7/IsekaiCompat` root, enabled only by `Poupun.IsekaiDungeonsAddon`. Definitions and names are unchanged; this package adds no second bonus implementation. The external exact-name compatibility gate is not fixed by this move. General grimoire drawing helpers remain in Content. Keep matching package versions so the old Content copy and this copy cannot load together.

### Logging Framework

Integrations owns discovery and calls to the optional RimWorks Logging Framework. It only examines already-loaded assemblies and checks provider readiness on each event; it does not bootstrap the framework or bundle it. Content retains `TM_Log`, its public message methods, reentrancy guards and `Verse.Log` fallback. Without this package, before adapter startup, or when the provider is unavailable or throws, warnings and errors still reach the game log. Developer-only trace events intentionally have no normal-log fallback.

The Content `TM_Log.TryWriteExternal` hook returns false unless an adapter accepts the event. It is an integration boundary, not a replacement for the public safe logging methods. No new Core API or saved state is introduced by this extraction.

## Guide for add-on developers and coding agents

### Choose the owner before writing code

- Core is the stable, vendor-neutral API. Read the shipped Core `Docs/API.md` and `Docs/AGENTS.md`; do not copy its saved data into another mod. Use non-copy-local references to Core and RimWorld.
- Content owns RWoM gameplay, class progression, pawn ownership, spell effects and official DLC behavior. General correctness fixes belong there even when a third-party mod exposed the bug.
- Integrations owns third-party detection, reflected vendor APIs, XML patches and vendor-specific Harmony interception. A filename containing a mod name is not sufficient reason to move shared gameplay or UI.
- Require matching Core and Content builds. `loadAfter` is only ordering; it neither installs a dependency nor prevents the loader from resolving a hard assembly reference.

### Add an optional adapter

1. Identify the installed package ID, assembly identity and actual API. Do not rely on a Workshop title, an old namespace or an API-only DLL copied by another mod.
2. Use the unconditional Integrations assembly only when the adapter can load with the vendor absent. Do not put vendor types in static fields, method signatures, attributes or compiler-generated delegate caches there.
3. Put hard references in a separate project and a conditional LoadFolders root. Keep external DLLs non-copy-local. Do not bundle vendor assemblies. Check root selection with the native loader, including either supported fork ID and no provider.
4. Preserve existing public Content entry points as thin neutral facades when add-ons may call them. Non-inlined facade hooks let the adapter supply optional behavior; the default must remain usable without Integrations.
5. Install patches from the owning assembly once. Use a unique Harmony owner and preserve ordering/priority. Do not patch the same gameplay action in both Content and Integrations.
6. Keep callbacks read-only unless the contract explicitly grants mutation. For cast admission, Core CastOwnership providers must not cast, spend resources or alter registrations during a query.

### Persistence and resource ownership

Do not rename serialized namespaces, assembly identities, defNames or Scribe keys during extraction. The VGE assembly remains `TorannMagic.VGE`; its components continue to derive from the same Content gameplay classes. Saved oxygen payment remains on the Content pump. A successful adapter move must not pay again, duplicate projectiles, lose passengers or reconstruct pawn progression from default values.

For oxygen output use the existing `IMagicalOxygenOutput` contract and preserve undelivered paid credit. For shield interception, prepare a valid landing plan before paying; commit only after payment. Neither interface makes the adapter the owner of the pawn or its saved inventory.

### Verification and delivery

Use the repository `tests/run-regression-tests.ps1` through pwsh with ArtifactsDir outside the repository. Use `-StagedRelease` for install-candidate checks so runtime loads the packaged binaries. Test absence, native provider presence, startup twice, scoped patch removal, save/load and payment ownership. Keep full-game, headless Scribe, serializer and live two-peer results separate. Do not describe a registration or byte-stream test as multiplayer-session acceptance.

Never mix old Content with new Integrations: old releases still contain the moved adapters. Upgrade Core, Content and Integrations together, back up changed and removed files, and verify installed hashes. Preserve v1.6 and user settings. Do not edit ModsConfig automatically. The player enables `RWoM Integrations` after Core, Content and the installed optional targets; Multiplayer Compatibility stays after it.

To roll back, close the game and restore every preexisting file from the installation backup manifest; remove only files recorded as newly created. Restore the entire matched set, not one DLL. If a restore fails, retain the backup and report the precise paths instead of continuing with a mixed release.
